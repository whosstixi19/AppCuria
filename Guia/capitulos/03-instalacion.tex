\chapter{Instalación paso a paso}\label{cap:instalacion}

\section{Obtención del código y preparación del entorno}
\begin{enumerate}
    \item Descomprima el paquete del proyecto en su carpeta de documentos o bien abra una terminal (PowerShell) para clonarlo con Git desde el repositorio oficial:
    \begin{lstlisting}[style=consola]
cd C:\Users\SuUsuario\Documents
git clone https://github.com/whosstixi19/AppCuria.git
cd AppCuria
\end{lstlisting}
    \item Verifique que dentro de la carpeta del proyecto se encuentren la subcarpeta \texttt{AplicacionCuria} (con el código fuente), el manifiesto \texttt{docker-compose.yml} y en la raíz el script de base de datos \texttt{BD.sql}.
\end{enumerate}

\section{Modalidad A: Instalación Local con Docker Desktop (Recomendada)}
Esta modalidad es el método más rápido, limpio y estandarizado para instalar el sistema en el equipo local de la parroquia o curia. No requiere instalar .NET SDK ni configurar pgAdmin manualmente, ya que todo el entorno se ejecuta en contenedores aislados.

\subsection{Verificación previa de virtualización}
\begin{enumerate}
    \item Abra el \textbf{Administrador de tareas} (\texttt{Ctrl + Shift + Esc}).
    \item Vaya a la pestaña \textbf{Rendimiento} y seleccione \textbf{CPU}.
    \item En la esquina inferior derecha verifique que indique \textbf{Virtualización: Habilitada}.
    \item Abra \textbf{Docker Desktop} y asegúrese de que el motor esté en ejecución (ícono de Docker en verde).
\end{enumerate}

\subsection{Puesta en marcha con un solo comando}
\begin{enumerate}
    \item Abra una consola de PowerShell en la raíz del proyecto (donde se ubica \texttt{docker-compose.yml}).
    \item Ejecute la orden de construcción y levantamiento de contenedores:
    \begin{lstlisting}[style=consola]
docker compose up -d --build
\end{lstlisting}
    \item \textbf{Inicialización automática:}
    \begin{itemize}
        \item El servicio \texttt{curia-postgres} monta el script \texttt{BD.sql} en \texttt{/docker-entrypoint-initdb.d/}, creando automáticamente la base de datos \texttt{curia}, las 24 tablas y el usuario administrador inicial con clave \texttt{Clave\_curia}.
        \item El servicio \texttt{curia-web} compila la aplicación ASP.NET Core 8 con soporte completo para generación de PDFs y expone los puertos \texttt{80} y \texttt{5155}.
    \end{itemize}
    \item Compruebe que ambos contenedores estén saludables ejecutando:
    \begin{lstlisting}[style=consola]
docker ps
\end{lstlisting}
    \item En el navegador de la máquina principal, ingrese a \url{http://localhost:5155} o \url{http://localhost} para comprobar el inicio de sesión.
\end{enumerate}

\subsection{Configuración de autoarranque con Windows}
Para que el párroco o secretaria no tengan que abrir consolas cada mañana:
\begin{enumerate}
    \item En la configuración de Docker Desktop (\textbf{Settings} $\rightarrow$ \textbf{General}), active la opción \textbf{Start Docker Desktop when you sign in to Windows}.
    \item Como el archivo \texttt{docker-compose.yml} tiene la directiva \texttt{restart: always}, los contenedores de la aplicación y la base de datos se encenderán solos en segundo plano al iniciar sesión en la computadora.
\end{enumerate}

\section{Modalidad B: Instalación Local Nativa (Plan B sin Docker)}
Si la computadora de la sede parroquial es antigua, tiene la virtualización bloqueada en la BIOS o no permite instalar Docker Desktop, se ejecuta la instalación nativa directa.

\subsection{Crear la base de datos \texttt{curia} en pgAdmin 4}
\begin{enumerate}
    \item Abra \textbf{pgAdmin 4} en la máquina principal y expanda en el panel izquierdo \textbf{Servers} $\rightarrow$ \textbf{PostgreSQL 18}.
    \item Haga clic derecho sobre \textbf{Databases} y seleccione \textbf{Create} $\rightarrow$ \textbf{Database...}.
    \item En el campo \textbf{Database}, escriba exactamente en minúsculas: \texttt{curia} y presione \textbf{Save}.
\end{enumerate}

\subsection{Ejecutar el script de base de datos (\texttt{BD.sql})}
\begin{enumerate}
    \item En el panel izquierdo de pgAdmin 4, haga clic derecho sobre la base de datos \texttt{curia} recién creada y seleccione \textbf{Query Tool}.
    \item Abra el archivo \texttt{BD.sql} (o copie su contenido en el editor).
    \item Asegúrese de no tener ningún fragmento sombreado y presione el botón \textbf{Execute script} (tecla \textbf{F5}).
    \item La pestaña \textbf{Messages} confirmará la creación exitosa de las 24 tablas.
\end{enumerate}

\subsection{Ejecución nativa y script de autoarranque en Windows}
Para que la aplicación funcione como un servicio permanente sin terminales abiertas:
\begin{enumerate}
    \item Compile y publique la aplicación en una carpeta limpia ejecutando en PowerShell:
    \begin{lstlisting}[style=consola]

\end{lstlisting}
    \item Cree un archivo ejecutable por lotes llamado \texttt{iniciar\_curia.bat} en \texttt{C:\textbackslash CuriaApp\textbackslash} con el siguiente contenido:
    \begin{lstlisting}[style=consola]

start /min AplicacionCuria.exe --urls "http://0.0.0.0:5155"
\end{lstlisting}
    \item Presione la combinación de teclas \texttt{Windows + R}, escriba \texttt{shell:startup} y presione Enter.
    \item Pegue dentro de esa carpeta un acceso directo al archivo \texttt{iniciar\_curia.bat}.
    \item Con esto, cada vez que se encienda la computadora, la aplicación web arrancará de forma automática en segundo plano.
\end{enumerate}

\section{Habilitar el acceso en Red Local y Configurar Nombre sin Costo}

\subsection{Aislamiento y seguridad por diseño}
Al tratarse de una instalación en red local (despacho parroquial), el servidor está \textbf{completamente aislado de Internet}. Ninguna persona externa puede acceder a los datos mediante datos móviles ni redes públicas a menos que se configure una VPN institucional.

\subsection{Apertura de puerto en el Firewall de Windows}
En la máquina principal donde corre el sistema, abra PowerShell como \textbf{Administrador} y ejecute una sola vez:
\begin{lstlisting}[style=consola]
New-NetFirewallRule -DisplayName "AplicacionCuria 5155" -Direction Inbound -LocalPort 5155 -Protocol TCP -Action Allow
\end{lstlisting}

\subsection{Acceso por Hostname (Nombre de equipo sin costo)}
No es necesario memorizar números de dirección IP (\texttt{192.168.1.X}). En la máquina principal consulte su nombre de equipo:
\begin{lstlisting}[style=consola]
hostname
\end{lstlisting}
Si el equipo se llama \texttt{SERVIDOR-CURIA}, todas las secretarias y sacerdotes de la oficina pueden ingresar directamente desde sus computadoras escribiendo en el navegador:
\begin{lstlisting}[style=consola]
http://SERVIDOR-CURIA:5155
\end{lstlisting}

\subsection{Dominio local amigable mediante el archivo \texttt{hosts} (Costo Cero)}
Si se prefiere una dirección institucional como \texttt{http://curia.local:5155} sin pagar registro de dominios:
\begin{enumerate}
    \item Asigne una dirección IP estática a la máquina principal (por ejemplo, \texttt{192.168.1.50}).
    \item En cada computadora cliente del despacho, abra el Bloc de notas como Administrador y edite el archivo \texttt{C:\textbackslash Windows\textbackslash System32\textbackslash drivers\textbackslash etc\textbackslash hosts}.
    \item Agregue al final la siguiente línea:
    \begin{lstlisting}[style=consola]
192.168.1.50    curia.local
\end{lstlisting}
    \item Guarde el archivo. A partir de ese momento podrán ingresar simplemente navegando a \url{http://curia.local:5155}.
\end{enumerate}

\section{Personalización de Escudos y Logos en Certificados PDF}
Cada parroquia o sucursal posee su propia identidad heráldica y escudos institucionales que deben figurar en las actas de Bautismo, Matrimonio, Primera Comunión y Confirmación.

\subsection{Ubicación del archivo de imagen}
En el código fuente, la imagen del membrete de los certificados reside en la ruta estática:
\begin{lstlisting}[style=consola]
AplicacionCuria/wwwroot/imagenes/logo_certificados.png
\end{lstlisting}
Las plantillas de generación de actas (\texttt{CertificadoBautizmo.cshtml}, \texttt{CertificadoCursilloMatrimonio.cshtml}, \texttt{CertificadoPaseDeNivel.cshtml}) consumen este recurso para incrustarlo en el encabezado del documento PDF.

\subsection{Personalización para la sede local instalada}
Para personalizar la instalación local de una parroquia específica:
\begin{enumerate}
    \item Prepare el escudo oficial de la parroquia en formato PNG transparente, con un ancho recomendado de 300 a 500 píxeles.
    \item Reemplace el archivo \texttt{logo\_certificados.png} en \texttt{AplicacionCuria/wwwroot/imagenes/} con el escudo propio de la sede.
    \item Si se utiliza Docker, reconstruya los recursos estáticos con \texttt{docker compose build app-curia \&\& docker compose up -d}. Si se utiliza la instalación nativa, copie la imagen a la carpeta \texttt{C:\textbackslash CuriaApp\textbackslash wwwroot\textbackslash imagenes\textbackslash}.
\end{enumerate}

\section{Arquitectura Multi-Sucursal ($N$ Parroquias) y Análisis de Costos en la Nube}

\subsection{¿Incrementa el costo en Google Cloud por tener múltiples parroquias?}
\textbf{No.} La carga transaccional del software eclesial es principalmente administrativa.
\begin{itemize}
    \item La instancia de máquina virtual estándar presupuestada (\textbf{\texttt{e2-medium} con 2 vCPUs y 4 GB de memoria RAM}) en Google Cloud Compute Engine tiene un costo mensual de aproximadamente \textbf{\$20.00 a \$24.00 USD}.
    \item Dicha infraestructura tiene capacidad computacional suficiente para atender de forma concurrente a decenas de parroquias y curias simultáneas bajo un esquema multi-inquilino sin necesidad de contratar servidores adicionales ni encarecer la factura de la Curia.
\end{itemize}

\subsection{Estrategia de aislamiento de datos (Multi-tenancy Lógico)}
Para segmentar la información de cada sucursal de modo que una parroquia únicamente acceda a sus propios registros mientras la Curia Central o Administrador General conserve visibilidad global:
\begin{enumerate}
    \item \textbf{Discriminador por tabla:} La tabla \texttt{parroquias} actúa como entidad matriz. En las tablas operativas (\texttt{usuarios}, \texttt{feligreses}, \texttt{actasbautismo}, \texttt{actasdematrimonio}, \texttt{agendas}) se añade una columna de relación:
    \begin{lstlisting}[style=sql]
ALTER TABLE usuarios ADD COLUMN parroquia_id INT REFERENCES parroquias(id);
ALTER TABLE feligreses ADD COLUMN parroquia_id INT REFERENCES parroquias(id);
ALTER TABLE actasbautismo ADD COLUMN parroquia_id INT REFERENCES parroquias(id);
\end{lstlisting}
    \item \textbf{Jerarquía de roles y control de acceso:}
    \begin{itemize}
        \item \textbf{SuperAdministrador (Curia Diocesana):} Su campo \texttt{parroquia\_id} es nulo o posee privilegio maestro. La interfaz le presenta un selector desplegable de parroquias para auditar cualquier sede o generar reportes diocesanos consolidados.
        \item \textbf{Administrador u Operador Parroquial:} Su usuario está estrictamente vinculado a una sola sede (\texttt{parroquia\_id = X}). En todas las consultas del backend, el sistema inyecta automáticamente el filtro \texttt{WHERE parroquia\_id = @parroquiaActiva}, garantizando que ninguna parroquia pueda visualizar ni modificar actas de otra jurisdicción.
    \end{itemize}
\end{enumerate}

\section{Procedimiento de Migración de Datos Local a la Nube (tras 6 meses)}\label{sec:migracion-cloud}
Si la parroquia opera el sistema en modalidad local durante un semestre y posteriormente la Curia decide centralizar toda la información en el servidor en la nube de Google Cloud, la migración de datos es sumamente sencilla y libre de incompatibilidades debido a que ambos entornos comparten el motor estándar PostgreSQL 17/18.

\subsection{Paso 1: Exportar el respaldo de 6 meses desde la máquina local}
Desde la máquina local (con Docker o nativo), genere un volcado binario consistente:
\begin{lstlisting}[style=consola]
# Si se uso Docker en la instalacion local:
docker exec -t curia-postgres pg_dump -U postgres -F c -b -v -f /tmp/curia_6meses.dump curia
docker cp curia-postgres:/tmp/curia_6meses.dump ./curia_6meses.dump

# Si se uso la instalacion nativa en Windows:
pg_dump -U postgres -F c -b -v -f "C:\CuriaApp\curia_6meses.dump" curia
\end{lstlisting}

\subsection{Paso 2: Transferir el archivo a Google Cloud}
Copie el archivo \texttt{curia\_6meses.dump} hacia la máquina virtual en Google Cloud mediante SCP, SFTP o descargándolo desde Google Drive institucional:
\begin{lstlisting}[style=consola]
gcloud compute scp curia_6meses.dump servidor-curia:~ --zone=us-central1-a
\end{lstlisting}

\subsection{Paso 3: Restauración en el contenedor en la Nube}
En la consola SSH del servidor en la nube, restaure la base de datos completa con la directiva \texttt{--clean} para reemplazar el esquema inicial con los datos históricos acumulados:
\begin{lstlisting}[style=consola]
docker cp ~/curia_6meses.dump curia-postgres:/tmp/curia_6meses.dump
docker exec -i curia-postgres pg_restore -U postgres -d curia -v --clean /tmp/curia_6meses.dump
\end{lstlisting}

\subsection{Paso 4: Verificación inmediata}
Al actualizar el navegador apuntando a la IP de Google Cloud, todos los feligreses, actas sacramentales, notas marginales, agendas y usuarios creados durante los 6 meses locales estarán inmediatamente disponibles en línea sin pérdida de información.

\section{Despliegue en la Nube con Docker en Google Cloud (Escenario 2)}\label{sec:despliegue-cloud}
El Escenario 2 traslada la infraestructura a una Máquina Virtual en Google Cloud Compute Engine, orquestada mediante Docker Compose. Este modelo elimina la necesidad de mantener un servidor físico local encendido de forma permanente en las dependencias de la Curia y otorga acceso global seguro a través de una dirección IP pública.

\subsection{Creación del proyecto e instancia de VM en Google Cloud}
\begin{enumerate}
    \item Inicie sesión en Google Cloud Console (\url{https://console.cloud.google.com}).
    \item En la barra superior, cree o seleccione un proyecto dedicado para la aplicación (por ejemplo, \texttt{AppCuria}).
    \item En el menú lateral o el buscador principal, diríjase a \textbf{Compute Engine} $\rightarrow$ \textbf{Instancias de VM} y presione el botón \textbf{+ Crear instancia}.
    \item Configure los parámetros de la máquina virtual:
    \begin{itemize}
        \item \textbf{Nombre:} \texttt{servidor-curia} (en minúsculas y sin espacios).
        \item \textbf{Región y Zona:} seleccione una región de bajo costo y baja latencia como \texttt{us-central1} (Iowa) o \texttt{us-east1} (Carolina del Sur).
        \item \textbf{Serie y Tipo de máquina:} serie \textbf{E2}, seleccionando el tipo \textbf{\texttt{e2-medium}} (2 vCPU virtuales, 4 GB de memoria RAM) para garantizar alta concurrencia multi-iglesia.
        \item \textbf{Disco de arranque:} haga clic en el botón \textbf{Cambiar}, seleccione \textbf{Ubuntu 24.04 LTS x86/64} (o 22.04 LTS), tipo de disco \textbf{Disco persistente equilibrado} y asigne un tamaño de \textbf{30 GB}.
        \item \textbf{Cortafuegos (Firewall):} en la sección de red, marque las dos casillas obligatorias: \textbf{Permitir tráfico HTTP} y \textbf{Permitir tráfico HTTPS}.
    \end{itemize}
    \item Haga clic en \textbf{Crear} y espere aproximadamente 30 segundos hasta que la instancia muestre el indicador de estado en verde y se le asigne su \textbf{IP externa} pública de Internet.
\end{enumerate}

\subsection{Integración y Despliegue Continuo (CI/CD con GitHub Actions)}\label{sec:cicd}
Para automatizar las actualizaciones del sistema sin necesidad de conectarse manualmente por SSH en cada cambio de código, se implementó un flujo de trabajo en GitHub Actions (\texttt{.github/workflows/deploy.yml}):

\begin{enumerate}
    \item \textbf{Integración Continua (CI):} Ante cada confirmación (\textit{push}) en la rama principal (\texttt{main}), un entorno virtual de GitHub compila y valida la solución en .NET 8.0, asegurando la integridad del código fuente antes de cualquier pase a producción.
    \item \textbf{Despliegue Continuo (CD):} Si la compilación es exitosa, GitHub Actions se autentica de forma segura mediante claves SSH en la máquina virtual de Google Cloud y ejecuta de forma autónoma:
    \begin{lstlisting}[style=consola]
cd AppCuria
git pull origin main
sudo docker compose up -d --build
\end{lstlisting}
    \item Este proceso actualiza la aplicación en la nube en menos de 90 segundos con cero tiempo de indisponibilidad para la base de datos.
\end{enumerate}

\subsection{Estrategia de respaldos automatizados en la nube}
En el Escenario 2, la información se almacena de forma persistente e independiente del ciclo de vida de los contenedores mediante el volumen Docker \texttt{postgres\_data}. Adicionalmente, para salvaguardar la información contra fallos mayores o permitir la migración de cuentas:
\begin{enumerate}
    \item Se establece una tarea programada en Linux (\texttt{cron}) que extrae un respaldo diario de la base de datos:
    \begin{lstlisting}[style=consola]
docker exec curia-postgres pg_dump -U postgres curia > /home/backups/curia_$(date +\%Y\%m\%d).sql
\end{lstlisting}
    \item Mediante la herramienta de sincronización \texttt{rclone} o la utilidad de línea de comandos de Google Cloud (\texttt{gcloud storage}), los archivos generados se transfieren automáticamente a un bucket de almacenamiento o a una carpeta designada en \textbf{Google Drive}, garantizando que el personal de la Curia conserve copia de los datos fuera del servidor.
\end{enumerate}
